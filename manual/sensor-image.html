What the image is

The exact array the library produces and expects, how it is formed, and how to supply your own detector data.

Format in one line

A (ny, nx) NumPy array from system.forward(...) — the readout of a single-photon sensor in short-gate binary mode, each pixel 0 or 1. forward raises if no lens images the point — a blank image is an error, not a measurement.

image = system.forward(s1, seed=1)   # binary, one bit per pixel
image.shape        # (ny, nx)  →  the addDetector(pixels=...) grid
image.sum()        # pixels that fired

How it is formed

  1. Each lens images the source to a Gaussian blob — centre from the chief ray, width from defocus (see the lens model).
  2. Each blob is evaluated as a pixel-convolved density times the pixel area: the per-axis variance is σ² + w²/12, where w is the pixel width. Folding the pixel's second moment into the blur keeps sub-pixel blobs from being aliased away, and keeps every operation inside the exp/sqrt/ratio arithmetic the solver accepts (there is no error-function integral anywhere in the model).
  3. The summed profile is normalised so its total equals photons — the detected count.
  4. A dark-count floor ε is added.
  5. Binary readout samples Bernoulli(1 − e^{−λ}) per pixel, with the explicit seed.

The photon count is the detected count

photons is Nγ, the number of photons that reach the sensor — the quantity an experimenter reads off — not the isotropic emission of the scintillation flash. The library normalises the underlying expected-count field (the left panel of the figure above) so it sums to exactly this value before the binary readout is sampled.

Fired pixels are not the photon count

A one-bit pixel saturates: it reports "at least one photon", however many arrived. The same 77-photon vertex on the same instrument fires

binningpixels firedwhy
12×1214 / 144many photons share the few pixels under each blob
24×2442 / 576less sharing, still saturated near blob centres
6688×4760 (realistic 6.9 µm)88 / 32 Mone pixel per photon; saturation is gone

So image.sum() under-counts at coarse binning, and the fitted photons from invert() is the better estimate of the detected count.

Binning decides identifiability

The choice of pixels is not cosmetic. Measured on the same 77-photon vertex, whole-volume search, no initial guess:

binning3-D error
12×1220.8 mm
24×240.93 mm
6688×4760, invert(sparse=True)0.055 mm
At coarse binning the one-bit likelihood can genuinely prefer a wrong nearby source over the true one — the data do not contain enough structure to tell them apart. This is a property of the sensor, not of the solver; the fix is more pixels, not more solve time. At fine pitch the model contains only the fired pixels (the dark side of the likelihood is summed in closed form), so finer binning does not inflate the model — see how the image reaches the solver.

Supplying your own data

Any 0/1 array works. Declare a detector whose pixels matches the array shape and whose size describes the same physical extent, then invert as usual:

import numpy as np, ria                       # your data comes in as a numpy array

image  = np.load("event_0421.npy")            # (ny, nx) of 0/1 — a real measurement
system = ria.imager()                         # then describe the instrument that took it
system.addScint(size=(50, 50, 50), working_distance=5.0)   # volume mm, lens gap mm
system.addLens(lenses=LENSES, blur_floor=0.12)              # the real lens records
system.addDetector(size=(46.15, 32.84),       # the sensor's real extent, mm
                   pixels=(image.shape[1], image.shape[0]), # grid = the array's shape
                   imaging_distance=20.477, dark_count=1e-9)  # S* mm, background rate
event = system.invert(image)                  # recover the vertex — no truth known
